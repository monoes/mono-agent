## S6: what does a real token look like?

Method: `scripts/spikes/s6-claims.ts`, a full PKCE login with and without `resource`.
Result: the table above, and what the brief expected, line for line. Without `resource`: `access: opaque, 32 characters`, `expires_in 3600`, a refresh token, and an EdDSA ID token (`aud` `"monoagent"`, `exp-iat=36000`, claims `acr,at_hash,aud,auth_time,exp,iat,iss,sub`). ## S1: can the `jwt()` plugin sign with a configured key, or can its key be pinned?

Method: read the plugin (`node_modules/better-auth/dist/plugins/jwt/types.d.mts`, `sign.mjs`, `adapter.mjs`, `utils.mjs`, `index.mjs`); `scripts/spikes/s1-key.ts` on the unmodified server; Task 6 runs it again with a pinned key.
Result:
- Default: one Ed25519 key, one `jwks` row (id is the `kid`, 32 characters; `expires_at` null because `rotationInterval` is unset, `utils.mjs:59`), created lazily at the first signing: the table had 0 rows before S6's first login, and the S1 run printed `jwks table rows: 1 before, 1 after`. Private half encrypted with `BETTER_AUTH_SECRET` (`utils.mjs:49-54`; the stored value is not a plain JWK). Published at `/api/auth/jwks` as `<kid> OKP/Ed25519 EdDSA`. A verifier holding only the public JWK checks a token (`node:crypto`, Ed25519: true); the ID token and a refreshed access token (200) carry the same `kid`. The generated key can be exported and pinned.
- The plugin signs with the newest live key `adapter.getJwks` returns (`adapter.mjs:12`) and `/jwks` publishes it; `adapter.createJwk` replaces the database insert, so it may refuse (`adapter.mjs:56`); `jwks.disablePrivateKeyEncryption` makes the plugin use the private half as stored (`sign.mjs:61`), so it can come from a secret. A custom `jwt.sign` needs `jwks.remoteUrl` (`index.mjs:24`), which makes the plugin's `/jwks` answer 404 (`index.mjs:116`) and the provider fetch its own keys over HTTP: not used.
- The plugin also signs a session JWT on every `get-session` (the `set-auth-jwt` header, `index.mjs:195-205`) unless `disableSettingJwtHeader` is set; nothing in `src`, `tests` or `public` reads it.
- The options Task 6 relies on exist: `types.d.mts` lines 68 (`disablePrivateKeyEncryption`), 177 (`disableSettingJwtHeader`), 199 (`getJwks`), 209 (`createJwk`): four matches, the precondition of Task 6.
Consequence: primary, a key from the secret `MONOAGENT_JWT_PRIVATE_JWK` through `adapter` (Task 6), plus an optional `MONOAGENT_JWT_PREVIOUS_PUBLIC_JWK` during a rotation. Fallback, pin the existing database key; it cannot do spec §4.7 step 1, because the next key is unknown until the server creates it. `disableSettingJwtHeader: true` limits the key's blast radius to the token endpoint.

## S2: can a refresh token issued without `resource` be exchanged with one?

Method: `scripts/spikes/s2-s3-refresh.ts`, section S2; the revoke route and concurrent refreshes in `scripts/spikes/s7-probe.ts` (P3, P9).
Result: yes. 200 and an audience-bound JWT, a rotated refresh token, and the audience then sticks (a later refresh without `resource` stays a JWT). A chain with no `resource` stays opaque, and becomes a JWT at its first refresh with one. Another resource: `invalid_target` (`requested resource https://example.com/other is not configured`). Presenting a rotated token again: `invalid_grant` (`invalid refresh token`), and the provider then deletes every MonoAgent refresh token of that account (the newer one answers `session not found`). That is the unmodified server, whose reuse interval is 0; Task 3 sets 300 seconds. Measured beyond the planning run:
- `/oauth2/revoke` of a live refresh token answers 200 with an empty body and revokes that one token; another sign-in of the account keeps working. Presenting the revoked token again ends every MonoAgent refresh token of the account, at the refresh grant (`invalid_grant`, `invalid refresh token`) and at the revoke route alike. A token revoked this way has no `rotated_at`, so Task 3's window never covers it.
- The revoke route answers 400 `invalid_request`, not RFC 7009's 200, for an unknown or already revoked token: `token not found`, or `refresh token revoked` with `token_type_hint=refresh_token`. Its `error.name === "BAD_REQUEST"` test (`authorize-Crqw4_bR.mjs:3603`) never matches, because better-call names every error `APIError`.
- Two refreshes of one token at the same moment: one 200, the other 400 `invalid_grant`, which mono-agent reads as a refusal; the other sign-in survives (3 of 3 trials, without a window; with Task 3's window, see the Constants row "Refresh token").
Consequence: D23 adoption needs no new sign-in. Adoption must delete the library vault's copy of the refresh token after the exchange: any later use of the old copy ends the account's sessions on every machine, once the 300-second reuse window of Task 3 has passed (inside it the provider answers the same request again with the same response, which is what covers a lost answer or a restart). The same holds for a copied session file and for a crash between the server's rotation and the client's write: spec §4.4's "the user signs in again (accepted)" means every install of the account is locked as refused until each signs in. Ruling R1 (S7) narrows each "every machine" and "every install" here to the install whose sign-in the replayed token comes from. `account logout` revokes one token (`/oauth2/revoke`, 200) and leaves the others alone, until the revoked token is presented again; a 400 from the revoke route means the token is already gone. One install must never present the same refresh token twice at once: not two refreshes, not a logout racing a refresh, and not a retry while the first request may still be running; the loser's `invalid_grant` is indistinguishable from a refusal (S7, residuals 2 and 3).

## S3: does the refresh grant refuse a blocked user, and does the provider rotate?

Method: `scripts/spikes/s2-s3-refresh.ts`, section S3 (block by SQL, which is all the route did); the rows in `scripts/spikes/s7-family.ts` and `scripts/spikes/s7-probe.ts` (P8).
Result, before Task 4: the provider rotates refresh tokens, and the refresh grant never looks at the user. A block deletes nothing (1 refresh row before, 1 after); the refresh of a blocked user answers 200 with a fresh JWT; a new web sign-in is refused (401); a web session that was still alive authorizes and gets fresh tokens (200). Ending the web session (sign-out, revoke-sessions, change-password) does not touch MonoAgent refresh tokens (200 each; the rows keep `revoked` empty and their `authorization_code_id`, only `session_id` becomes null), so signing out of monoes.me never locks an install. The provider's session-delete hook revokes only the session's refresh tokens that lack `offline_access`, and its opaque access-token rows (`authorize-Crqw4_bR.mjs:259-260`; read, not measured); every MonoAgent refresh token carries `offline_access`.
Result, after Task 4 (the plan's expectation, which Task 4's specs verify; not part of this run): the block deletes the user's tokens and web sessions, and the refresh answers `invalid_grant`; so does an audience-bound grant for a blocked user whose tokens survived. Grants without a `resource` are covered by the deletion only.
Consequence: only a block, `/oauth2/revoke`, 30 days without use, a replay, or a replay of the authorization code a chain came from (S7) ends a MonoAgent refresh token. A machine offline for more than 30 days gets `invalid_grant`: locked as refused, not as unreachable.

The request handling the rule mirrors (read):
- A hook receives the body as better-call parsed it, before validation: a repeated field keeps its last value (`better-call/dist/utils.mjs:36-38`). The handler sees the schema's output, built inside the endpoint (`better-call/dist/context.mjs:10-17`).
- The token schema trims `grant_type` (`authorize-Crqw4_bR.mjs:4580`) and nothing else: the provider hashes `refresh_token` as sent (`:4588`; T3).
- The provider resolves its caller from the raw form: the non-empty `client_id` values, two or more refused (`utils-B77ebneW.mjs:559-561`). So `client_id=monoagent&client_id=` is `monoagent` to it and `""` to a hook (R3, T2).
- The revoke route treats a `token_type_hint` other than `access_token` and `refresh_token` as none (`authorize-Crqw4_bR.mjs:3567`). It trims the token and strips a `Bearer` or `DPoP` scheme before its lookup (`stripAccessTokenAuthorizationScheme`, `:3573`; exported by `better-auth/oauth2`; `@better-auth/core/dist/oauth2/dpop.mjs:58-84`; R4 to R6). Its schema transforms neither field (`:4850-4851`).
- The revoke route punishes the caller's client for the row's user, whatever client the row belongs to (`:3505-3506`). In R7 the user's MonoAgent rows went and the other client's stayed.
- Both endpoints set `cloneRequest: true` (`:4578`, `:4844`), so a hook can read the raw form through `ctx.request.clone()`.

The rule:
1. **Shared.** Find a row by the `sha256Base64Url` of the value (the provider's default `storeTokens`; no prefix or `formatRefreshToken` is configured). Its family is the refresh rows with its `client_id`, `user_id` and `authorization_code_id`. Delete, in one `db.batch`, the access rows whose `refresh_id` is one of them, then those refresh rows; repeat the refresh-row delete once after the batch (it narrows residual 1). Never filter on a null `authorization_code_id`. The provider's adapter turns `null` into `IS NULL` (`@better-auth/drizzle-adapter/dist/index.mjs:159`, `:202`, `:244`) and would sweep every null-key chain of the user. Drizzle's `eq(column, null)`, which the hook's own `db.batch` would use, binds `= NULL` and deletes nothing (`drizzle-orm/sql/expressions/conditions.js:20-22`). Either way, for a null key, delete the presented row and its access rows by `id`: the dead token is still punished once, though a successor holding no key survives. With Task 7 writing a key and the owner check of answer 2 at 0, that branch is unreachable.
2. **Token route, decided on the row.** Match `ctx.path === "/oauth2/token"` and `String(ctx.body?.grant_type ?? "").trim() === "refresh_token"`, and never read `ctx.body.client_id`. Act if and only if the row of `ctx.body.refresh_token` (a string, hashed as sent) meets all of these:
   - it exists, and its `client_id` is `monoagent`;
   - its `expires_at` is in the future;
   - `revoked` is set;
   - it is outside the window, judged 10 s early: not (`rotated_at` and `rotation_replay_expires_at` set, and `rotation_replay_expires_at >= now + 10 s`).

   mono-agent never retries after 240 seconds, so no honest retry falls in the last 10 of the 300.
3. **Acting on the token route.** Delete the family, then `throw new APIError("BAD_REQUEST", { error: "invalid_grant", error_description: "invalid refresh token" })`. Otherwise return nothing: the provider replays inside the window or answers without punishing (`:2120-2158`). Every path to `:2160` for a MonoAgent row meets these conditions, because the provider requires the row's client to be the caller (`:2124`). The resource and scope checks are not mirrored, and neither is client validation (`utils-B77ebneW.mjs:636-657`: a disabled client, a scope outside the client's, a grant it may not use, the auth method). That only makes the hook end a dead token's family where the provider would have ended nothing.
4. **Revoke route, owned by the hook.** On `ctx.path === "/oauth2/revoke"`, unless `token_type_hint` is exactly `access_token` (any other value reaches the refresh path, `:3567`, `:3588`), normalize the token with `stripAccessTokenAuthorizationScheme` (as `:3573` does) and look up its row.
   - Handle the request if and only if the row exists and the caller is `monoagent`. The caller is the single non-empty `client_id` of the raw form when the request is form-encoded. With two or more, return nothing: the provider refuses with `invalid_request` (`utils-B77ebneW.mjs:560`). With none, it is a non-empty `ctx.body.client_id` (an `auth.api` call).
   - Otherwise return nothing: the provider then punishes only the caller's own client, never `monoagent` (`:3506`).
   - The provider refuses client authentication for the public `monoagent` client: Basic credentials or a client assertion (`utils-B77ebneW.mjs:640-641`), a `client_secret` (`:648`). Handling such a request anyway only ends the presented token's family.
5. **Handling a revoke.**
   - A `monoagent` row, live or revoked, inside or outside the window, expired or not: delete its family. Answer 200 with an empty body if it was live, or the provider's 400 `invalid_request` if it was revoked: `refresh token revoked` with the hint `refresh_token`, `token not found` without it.
   - Another client's row: delete nothing, and answer the same way (R7).
   - The 200 must be a truthy return value, such as `new Response(null, { status: 200 })`: only a truthy object without a `context` key ends the pipeline (`dispatch.mjs:91-103`, `:218-223`).
6. **Why this closes both routes.** `revokeRefreshToken` never runs for a `monoagent` caller's row, so neither `:3506` nor `:3527` fires for MonoAgent. Deleting instead of marking `revoked` leaves no revoked row behind: a refresh racing the logout finds no row (`:2120`) or loses its compare-and-set (`:1591`), and ends nothing.
7. **Task 7** adds `authorizationCodeId: \`email-claim:${claim.id}\`` to its `oauthRefreshToken` insert (P7: the planned row has none). The value can never equal a code hash, so `revokeTokensIssuedForAuthorizationCode` never matches it.

Residuals:
1. **A rotation that races the delete.** A rotation whose compare-and-set lands just before the family delete can insert its successor just after it, leaving a live row in the ended family (the provider's own TODO, `introspect-6ew7sakf.mjs:1487-1494`). The second sweep narrows it; nothing closes it.
2. **A retry arriving while the first request is still in flight.** Inside the window, a retry that reads the row after the first request's rotation but before its answer is stored (`:1881-1886`) gets `invalid_grant` (`:2155-2158`). No family ends, but mono-agent reads a refusal. The B plans must not retry while the first request may still be running.
3. **A logout racing a refresh in one install.** Under the first rule, a concurrent revoke could mark the row `revoked` between the hook's read and the provider's (`:2146`), and a concurrent rotation could revoke it before `authorize-Crqw4_bR.mjs:3505`; either ended the account. This rule's delete closes both (point 6). The losing request still gets `invalid_grant` or a 400, so the B plans serialize logout with refresh per install as well.
4. **The window's edge.** The hook and the provider judge the window at slightly different moments, so a replay at the very end could pass the hook as inside and reach `:2160` as outside. Judging the window 10 s early (point 2) closes that, as long as the two checks run less than 10 s apart.
5. **JWT access tokens** of an ended family stay valid until `exp`, at most 3600 seconds, as today.

## Decisions taken (the lead, 2026-10-05; the fourth by ruling R1 of 2026-10-07)

1. `refreshTokenReuseInterval: 300` (Task 3), the owner's to lower, together with the client's `pendingRetryWindow`. The client retries a lost response for as long as 240 seconds after the first send (spec A24), so a 60-second window would leave the later retries presenting a rotated token and ending every session of the account. Inside the window a replay of a used token, a thief's included, gets the same response; it does not cover an explicitly revoked token (`/oauth2/revoke`, a block), which answers `invalid_grant` at once.
2. The email-code route (Task 7) is the one server change beyond spec §5. For the MonoAgent client's `offline_access` claim it returns a `refresh_token`, which the client trades at the token endpoint with `resource` (B1b's design), and it honors a `resource` in the verify body (one call, the token endpoint's own answer). Without `resource` the opaque access token is unchanged; a blocked account is refused.
3. Extras approved: `disableSettingJwtHeader`; deleting a blocked account's web sessions; the optional previous-key secret for a rotation; the audience as a database row plus a client link (migration 0017). Spec §5 item 1 says `oauthProvider` "accepts the resource"; it is a row and a link, not an option.
4. Refresh-token families (ruling R1 of 2026-10-07): a replay of a rotated-away refresh token after the reuse window ends only that token's family, not every MonoAgent refresh token of the account, which removes the 5xx trade-off of the client's A24 and shrinks each of its residuals to "that install signs itself out". S7 measures what names a family; the lead writes Task 3's steps for it from S7's findings before Task 3 is dispatched. The client keeps A24 and A25 as defence in depth and changes no constant until the server has shipped and been measured.
